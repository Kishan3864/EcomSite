## 1. Deployment rules

- The agent has **NO access to the production server**. Never ssh/scp/rsync, never `npm run deploy` (it SSHes), never create deploy keys or CI that deploys.
- Kishan deploys by hand. Flow: make the change → gate (section 5) → commit → `git push origin main` **only when he says push** → give him the server command → wait for the pasted output → fix forward if it failed.
- The exact server command (run as `flexyuser`), always given in a block labelled "🖥️ Server par run karo":

  ```bash
  cd ~/ecom.flexypdf.com && bash deploy/deploy.sh 2>&1 | tail -60
  ```

  Rollback for him: `cd ~/ecom.flexypdf.com && bash deploy/rollback.sh`
- Production: VPS user `flexyuser`, app dir `~/ecom.flexypdf.com`, PM2 app `weekendcart`, port 3040, **fork mode, 1 instance** (`deploy/ecosystem.config.cjs`). deploy.sh runs `npm ci`, `prisma migrate deploy`, `npm run db:seed` (essentials only, never demo), build, PM2 reload, health check, auto-rollback.
- **deploy.sh changes need two deploys**: the script is already running (from a copy of itself) when it pulls its own new version, so an edit to deploy.sh takes effect from the deploy AFTER the one that ships it. Anything that must work on the FIRST deploy goes somewhere the old script already calls — that is why the image-cache link is an npm `postbuild` step and not a line in deploy.sh. Deploy with maintenance mode OFF unless he says otherwise.
- Always tell him plainly what changes on the live site the moment a deploy lands, especially anything that could surprise a shopper mid-session.
- He reviews on the live site, not locally. Local DB: Postgres 16 cluster in `.pgdata` on port **5433** (`npm run db:start`; it is stopped at the start of every session). Local admin login: `admin@mayura.in` / `Mayura@2026`. psql: `C:\Program Files\PostgreSQL\16\bin\psql.exe`.
